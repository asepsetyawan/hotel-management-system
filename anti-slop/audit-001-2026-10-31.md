# Stay OS antislop audit 001

Date: 31 October 2026, Asia/Jakarta. Mode: **after**, explicitly selected in this chat. Filters: antislop core and antislop-ui.

This is an assessment of the existing application, not a redesigned interface or release approval. Application source was left unchanged. Findings require approval by number before implementation.

## Direction and scope

Reading this as: hotel operations for owners, front desk, and housekeeping, plus a direct-booking website for guests, in a calm forest-green and cream hospitality language, dial **ENERGY 1 / RHYTHM 2 / MOTION 1**. These are audit interpretations of `DESIGN.md`, not new owner-approved design specifications. Staff tables remain predictable; guest pages use more editorial composition.

Keep the established green/cream palette, serif public headings, compact operational typography, restrained corner sizes, and arched illustration motif. Those choices already have a product-specific rationale in `DESIGN.md`. A replacement aesthetic or an additional theme is not needed to resolve the findings.

Inspected all Blade views, shared CSS/JavaScript, routes, relevant controllers, and demo seeding. Ran the existing feature/unit suite: **25 tests, 81 assertions, all passing**. Browser measurements cover 15 routes at 1440px, 390px, and 320px, totaling 45 page/viewport observations. The responsive measurement run used reduced motion to avoid measuring a drawer midway through its resize transition. Screenshots were visually inspected. Contrast values below were calculated from source color pairs using relative luminance, not estimated from screenshots.

Priority follows the skill's rule tiers: **HIGH** for Hard Gates, **MEDIUM** for Purpose Gates, **LOW** for Quality Locks. Priority is not a general security or business severity rating.

## Numbered findings

### 1. HIGH: secondary text and status labels fail contrast

**Rules:** R-25. **Reason:** essential operational details and guest booking copy fall below the 4.5:1 requirement for normal text.

Evidence: `public/assets/app.css:2`, selectors `.muted`, `.page-heading p`, `.panel-header p`, `.badge.*`, `.public-hero p`.

| Text | Foreground / background | Measured ratio |
| --- | --- | --- |
| Muted text on a white panel | `#829087` / `#ffffff` | 3.34:1 |
| Staff page description | `#92998c` / `#f6f7f3` | 2.73:1 |
| Panel subtitle | `#9a9f92` / `#ffffff` | 2.71:1 |
| Confirmed status | `#9c8b49` / `#faf6e6` | 3.13:1 |
| Clean status | `#648457` / `#eff5e7` | 3.79:1 |
| Dirty status | `#a7705c` / `#faf0e9` | 3.66:1 |
| Checked-out status | `#7c8e9c` / `#eef3f6` | 3.03:1 |
| Public hero description | `#8a927e` / `#faf9f4` | 3.07:1 |

Proposed fix: darken secondary and status foregrounds within the existing palette, then verify every shared text treatment and focus indicator on its actual background. Small text does not qualify for the large-text exception.

### 2. HIGH: several phone layouts overflow the page

**Rules:** R-03. **Reason:** the document itself scrolls sideways instead of keeping overflow within the intended table container.

Measured document widths after layout settled:

| Route | Viewport | Document width |
| --- | --- | --- |
| `/login` | 390px | 410px |
| `/login` | 320px | 410px |
| `/app` | 390px | 504px |
| `/app` | 320px | 504px |
| `/app/calendar` | 390px and 320px | 712px |
| `/app/rooms` | 320px | 325px |

Evidence: `public/assets/app.css:2`, `.login-card{width:360px}`, grid min-content sizing, `.room-grid`, `.room-details`, and nonwrapping controls; responsive overrides at lines 5–6. The calendar measurement includes table-related overflow; the problem is the increased document width, not the presence of a horizontally scrollable table itself.

Proposed fix: bound the sign-in form to its container, allow dashboard grid children to shrink, confine availability overflow to `.table-scroll`, and reflow room actions/details at narrow widths. Do not conceal the problem with a blanket body overflow rule. Evidence: `evidence/overview-320.png` and `evidence/login-390.png`.

### 3. HIGH: primary mobile controls miss the 44px target

**Rules:** R-03. **Reason:** frequent actions retain desktop-sized hit areas on phones.

Evidence: `public/assets/app.css:2` and line 6. `.icon-button` is 32×32px; the public Reserve your stay button measures 38.5px high; Find a room is 42px high. Sidebar links are 37px high, and the property selector is 24px high. On the 390px housekeeping page, the select is 34px high and Update is 34.5px high. These are element measurements, not icon measurements.

Proposed fix: give mobile actions and their clickable labels a minimum 44px target while retaining appropriately sized icons and readable spacing. Include menu, dialog close, housekeeping updates, reservation actions, and room-map links in the verification.

### 4. HIGH: the mobile drawer hides its own toggle and leaks keyboard focus

**Rules:** R-32, R-39. **Reason:** navigation can be opened but has no dependable dismissal or focus model.

Evidence: `resources/views/layouts/admin.blade.php:4`, line 15; `public/assets/app.js:5`; `public/assets/app.css:6`.

Browser reproduction: open Toggle navigation at 390px. The fixed drawer covers that toggle. Trying to click the toggle again is intercepted by the drawer's brand. Escape leaves `.sidebar.open` in place. There is no internal close button or clickable dismiss backdrop. The toggle has neither `aria-expanded` nor `aria-controls`. With the drawer closed, Tab from the skip link focuses the offscreen brand at x = -232px.

Proposed fix: add a reachable close control and dismissal behavior, announce expansion, remove closed navigation from focus order, and manage focus consistently while open and on close.

### 5. HIGH: dialogs have visible headings but no accessible names

**Rules:** R-39. **Reason:** screen readers encounter unnamed dialog containers even though the visual title is present.

Evidence: `resources/views/layouts/admin.blade.php:23`, `resources/views/public/hotel.blade.php:6`, `resources/views/admin/reservations.blade.php:7`, room and settings dialogs. Browser inspection of the guest booking dialog confirms `aria-label=null` and `aria-labelledby=null`. Its heading is not programmatically associated with the dialog.

Proposed fix: give each dialog heading a unique ID and connect it with `aria-labelledby`. Preserve native modal focus handling and Escape, which already work for the tested booking dialogs.

### 6. HIGH: the front-desk tab widget has incomplete semantics and keyboard behavior

**Rules:** R-39. **Reason:** controls advertise a tab interface without corresponding tab-panel relationships or expected directional navigation.

Evidence: `resources/views/admin/overview.blade.php:12`, `public/assets/app.js:8`. Controls use `role="tab"` and selected state, but omit `aria-controls` and a roving tab stop; content containers omit `role="tabpanel"` and labeling relationships. JavaScript only handles clicks. After focusing Arrivals and pressing ArrowRight, focus remains on Arrivals and Departures remains unselected.

Proposed fix: implement the complete tab interaction and associations, or simplify to native buttons with truthful expanded/pressed semantics. Mouse activation of both tabs already works.

### 7. HIGH: fictional demo records look like real inventory and customers

**Rules:** R-17, R-38. **Reason:** documentation discloses the seed data, but the actual guest and staff screens do not label it as demonstration content.

Evidence: `database/seeders/DatabaseSeeder.php:15` creates invented staff identities; lines 19–37 create fictional published hotels, guest records, rates, stays, and payments. `README.md` explains this clearly. The marketplace, hotel pages, and staff dashboard present those records without an equivalent visible demo notice. A footer saying Local workspace identifies the environment, not fictional data.

Proposed fix: attach an explicit demo-data designation to seeded content and show an appropriate notice where it appears. Keep real future records separate. Preserve the distinction between calculated database metrics and invented marketing metrics: the current dashboard calculations do use the database.

### 8. HIGH: missing first-run guidance and visible pending feedback

**Rules:** R-27. **Reason:** some valid empty installations produce blank sections, while submission feedback is only a disabled button.

Evidence: `resources/views/admin/rooms.blade.php:6`, line 7; `resources/views/admin/housekeeping.blade.php:5`; `resources/views/admin/calendar.blade.php:5`; `resources/views/admin/reports.blade.php:6`. These use loops without specific empty content for room types, rooms, or report rows. `public/assets/app.js:13` disables a submit button, leaves its label unchanged, and re-enables it after eight seconds regardless of request state. An intercepted guest submission confirmed that the disabled button still says Confirm reservation, with no busy attribute or status announcement. That request was blocked in the browser and did not create a booking.

Proposed fix: give each first-run screen the cause and a role-appropriate next action. Show explicit pending text for submissions, prevent duplicates for the actual request lifecycle, and preserve an actionable error path. Ordinary server-rendered tables do not need invented asynchronous skeletons. Existing destination-search and guest-directory empty messages are useful and should be retained.

### 9. HIGH: shared control affordances and standalone document semantics are incomplete

**Rules:** R-39. **Reason:** several controls have hidden-only labels or missing interaction states, and standalone pages omit the document structure required by the filter.

Evidence: `public/assets/app.css:2` sets pointer only for buttons, with no shared pointer rule for selects, checkboxes, or their labels and no explicit pressed `:active` treatment. `resources/views/layouts/admin.blade.php:5`, `resources/views/admin/housekeeping.blade.php:5`, and rate controls in `resources/views/admin/rooms.blade.php:6` use screen-reader-only labels where the skill requires visible labels. This is a stricter filter requirement, not a claim that every hidden label alone violates WCAG. `resources/views/public/login.blade.php:1` contains two h1 elements and no main landmark; `resources/views/admin/invoice.blade.php:1` uses an article without the required page landmarks.

Proposed fix: complete shared enabled, hover, active, focus, and disabled treatments; provide compact visible field context; and correct the sign-in/invoice document structure without redesigning their appearance.

### 10. HIGH: public hero images lack explicit high fetch priority

**Rules:** R-40. **Reason:** the largest first-screen image has the browser's default priority instead of the priority required by the filter.

Evidence: `resources/views/public/marketplace.blade.php:2`, `resources/views/public/hotel.blade.php:4`. Both hero images are real HTML images, are not lazy-loaded, and reserve space through `.hero-art{aspect-ratio:1/1}`. Their measured `fetchPriority` is `auto`, not `high`. Room images at hotel line 5 also lack intrinsic width/height or an explicit aspect ratio on desktop; stretched `height:100%` is not a stable intrinsic media ratio.

Proposed fix: add `fetchpriority="high"` to the hero and stable dimensions/ratios to room illustrations. Keep below-fold media from competing unnecessarily. Lighthouse and field Web Vitals were **not measured**; this finding makes no numeric speed claim.

### 11. HIGH: the overview links unpublished properties to a guaranteed 404

**Rules:** R-24, R-26. **Reason:** Visit your website is always offered even when the selected property's public page is inaccessible.

Evidence, source inspection: `resources/views/admin/overview.blade.php:19` renders `/hotels/{{ $property->slug }}` unconditionally. `app/Http/Controllers/PublicController.php:10` requires `published=true`. The website management page already handles the distinction correctly in `resources/views/admin/website.blade.php:5`.

Proposed fix: apply the same published/draft treatment to the overview, with a working configuration destination for staff permitted to publish. The state was traced in source; no property was created or unpublished during this audit. The earlier suspected confirmation-page `#rooms` issue was discarded: that page receives no `$property` variable and currently renders the collection header.

### 12. MEDIUM: decorative glyphs, permanent notification dot, and repeated arrows lack recorded purposes

**Rules:** R-04, R-08, R-09. **Reason:** several recurring attention cues have no documented informational or hospitality-identity role.

Evidence: `resources/views/layouts/admin.blade.php:12` adds a sparkle to generic help copy; line 15 always renders a notification dot regardless of outstanding work; `public/assets/app.css:2` adds a large starburst with `.tip-panel:after`. Arrow glyphs occur across the guest CTAs and unrelated staff links, without a documented distinction between direction, external navigation, and decoration.

Proposed fix: remove the noninformational cues or record their concrete brand/hierarchy purpose. Tie any notification indicator to a real condition. Preserve domain icons and status colors when they communicate real room or reservation states. The icon library's consistent stroke alone is not treated as a defect.

### 13. LOW: the operational overview carries promotional filler and competing focal points

**Rules:** R-05, R-20; C-3. **Reason:** a front-desk screen spends mobile scroll space promoting features already present in navigation.

Evidence: `resources/views/admin/overview.blade.php:5` starts with four equal metric cards before the front-desk work; lines 19–20 add Your next guest and Your connected workspace beneath operational data. The latter repeats booking, marketplace, and mobile navigation. The desktop screenshot shows a chart/table/stat-card shell with a promotional card competing against arrival work; on a phone these panels extend the page further.

Proposed fix: make arrivals, due departures, or rooms needing action the clear operational focal point; reduce or remove repeated promotional panels. Retain genuinely useful metrics and the question-specific seven-day booking chart. This is a hierarchy refinement, not a recommendation to discard the established staff shell.

### 14. LOW: staff copy uses a prohibited buzzword and vague actions

**Rules:** R-15, R-16. **Reason:** operational labels should identify the real action instead of promoting the product.

Evidence: `resources/views/admin/overview.blade.php:19` describes direct bookings as effortless. `resources/views/layouts/admin.blade.php:12` says Explore your workspace while routing to different destinations by permission. `resources/views/admin/overview.blade.php:15` says Explore reports.

Proposed fix: replace the buzzword with a concrete description and name the destination/action, such as Edit hotel website, Open mobile workspace, or View reports, as appropriate. The copywriting filter can be applied narrowly to these texts without rewriting the hotel's entire voice.
